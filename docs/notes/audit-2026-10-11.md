# Audit: what Margin is, where it goes in circles, and what to build next (2026-10-11)

Every number below was computed from the 56 real recorded runs (`runs/*/events.jsonl`, `runs/*/checkpoint.json`, the ledger), excluding
infrastructure failures, the four fault and resume demos and the smoke test. The scripts are kept outside the repository; the method is
described next to each finding so it can be repeated.

## 1. What exists

| Part | State |
|---|---|
| Agent loop and tools | `read_file`, `search_code`, `edit_file`, `write_file`, `run_tests`, `git_diff`, plus `graph_impact` on arms B and C. No tool runs a snippet of code. |
| Verifier | baseline-aware: a fix counts only if the target tests pass and nothing that passed before fails, is skipped or goes missing; test files and test infrastructure are reverted before judging; a probe checks pytest is not shadowed |
| Quote and governor | leave-one-out quote from past arm B runs; governor ladder CONTINUE, DOWNGRADE (60% of the quote's top), NARROW (85%), ABORT |
| Recovery | retries with backoff, flaky re-run, test-timeout fallback, kill and resume from a checkpoint with spend counted once |
| Evidence | ledger snapshot, results and receipts pages, neatlogs traces and screenshots, one public Entire checkpoint, cfo.ai plan |
| Size | 3,348 lines of source, 3,282 lines of tests (302 tests), 73 commits, 9 CLI commands |
| Spend | $7.13 on the 56 real runs; about $7.3 of the event's $20 allowance in total |

What it is not: a hosted service, an API or an MCP server, or a tool for issues without tests that must go from failing to passing.

## 2. Where the agent goes in circles

### Finding 1: the agent does not stop when the job is done
In the 28 verified arm B and C runs that kept their whole conversation, **18% of the spend ($0.39 of $2.16) came after the first test run in
which every target test passed and no new failure appeared**. At that moment the run was already a verified fix. Worst cases: `marshmallow-2249`
on arm B made 12 more calls after its first green run and stopped only at the 30-turn limit; `moreitertools-1214` on arm A made 14 more.

*Method:* the turn of the first `run_tests` result reading "Target tests: 0 failing" and "New failures vs baseline: none", then the cost of
every model call after it.

### Finding 2: when the agent is stuck, the governor makes it weaker and forgetful
On "no progress at 60% of the cap" the governor's DOWNGRADE does two things: it switches to the fallback model (`nova-2-lite`, a third to a half of
the main model's price) **and** replaces the whole conversation with a short digest of the issue, the diff and the last test result. Four arm C
runs were downgraded. Three of them then failed at the 30-turn limit (`sqlparse-772`, `tomlkit-261`, `marshmallow-2249`). Arm B, which has no
governor, solved two of those three tasks (`tomlkit-261`, `marshmallow-2249`). With one run per task this is not proof, but three of the four arm C
failures followed a downgrade; the fourth (`sqlparse-826`) had no governor action and ran out of turns.

### Finding 3: failures are mostly running out of turns, not literal repeat loops
10 of the 12 failed runs hit the 30-turn limit; 6 of the 12 ended with a test that had passed before now failing, 4 of them among the
turn-limit runs. In the saved conversations, exact repeats (the same tool with the same arguments again) are as common in solved runs as in failed
ones (3.3 against 3.4 per run), and so are streaks of the same tool (3.2 against 3.3). So a simple "you repeated yourself" detector would not separate failing runs
from working ones; being stuck shows up as no progress over many turns.

### Finding 4: the agent wants to run code and cannot
Eleven tool calls were refused because the agent tried to create a debugging script (`test_debug.py`, `debug_test.py`,
`scripts/debug_test.py`): it wanted to call the library directly, as the issue's own reproduction does. Nine of the eleven were on
`sqlparse`, the hardest repository, and refused calls are more frequent in failed runs than in solved ones (0.5 against 0.1 per run). There is no tool that runs a snippet; `run_tests` only runs the test suite.

### Finding 5: on arm A, regressions are invisible until the verdict
Arm A's `run_tests` runs only the target tests, by design. Both of arm A's failures that did not hit the turn limit ended with a test that had
passed before now failing, which arm A's `run_tests` never showed the agent. Arms B and C run the whole suite and report new failures.

## 3. Other gaps (beyond loops)

| Gap | Effect | Status |
|---|---|---|
| A task needs tests that go from failing to passing | Margin cannot judge an issue that has no such tests | scope limit, stated in the README |
| Test code runs as the same user, network not blocked | a malicious repository could do harm on the machine | stated in `EVIDENCE.md` |
| Issue text is not screened for instructions aimed at the agent | prompt injection through an issue | stated in `EVIDENCE.md` |
| One run per task, 16 tasks, one cheap model | differences of one or two tasks are inside run-to-run noise | stated everywhere results appear |
| The quote's top caps the spend | a quote that undershoots ends a run that needed a little more (`marshmallow-2249` on arm C) | measured, `docs/notes/arm-c-evaluation.md` |
| Client-side API timeouts | the cost of three runs is a lower bound | flagged on the results page |
| Graph search output tells the agent to run `python -m pytest ...` | the agent has no shell; it uses `run_tests` instead | harmless so far |
| The Anthropic provider path | never run live | stated |

## 4. Proposal: learning from failures, and one agent guiding another

Each item answers one finding. All of it would be measured as a new arm, **D**, on the same 12 evaluation tasks, without re-running or editing
A, B or C. D's quote, cap and pricing stay as in C.

| # | Change | Answers | Kind | Cost to run |
|---|---|---|---|---|
| 1 | **Stop when verified.** After a `run_tests` result with every target passing and no new failure, the harness tells the agent the fix verifies and to finish with one sentence; if it carries on for two more turns, the harness ends the run itself. | Finding 1 | rule, no model | saves about a sixth |
| 2 | **A coach instead of a downgrade.** When the governor sees no progress, a stronger model (`claude-sonnet-4.6` on the proxy, about $0.03 a call) reads a compact digest of the run so far (issue, diff, last test output, the last few tool calls) and writes a diagnosis and a next step; the worker keeps its model and its conversation and gets the note. At most two coach notes per run, both counted against the cap. | Finding 2 | second agent guiding the first | about $0.03 to $0.06 per stuck run |
| 3 | **A reproduce tool.** `run_python`: runs a short snippet inside the worktree with the same scrubbed environment, timeout and output limit as the tests, so the agent can call the library the way the issue does. | Finding 4 | capability | negligible |
| 4 | **Lessons from past runs.** After each run, a short post-mortem by the coach model turns what went wrong (or what finally worked) into one to three general lessons, tagged with the repository and the failure type. Before a new run, the lessons for that repository are added to the first prompt. Measured leave-one-out: a task never sees lessons written about itself, the same rule the quote follows. | self-learning | cross-run memory | about $0.01 per post-mortem |
| 5 | **A second attempt guided by a reviewer.** If the final verdict fails and budget remains, the reviewer reads the failing tests and the diff and briefs a second attempt. Only bills if the second attempt verifies. | "one agent fixing another" | second agent, optional | up to one more run on failures |

Recommended order: 1, 2 and 3 first (they answer measured problems and are small), then 4 with leave-one-out measurement, then 5 if time and
budget remain. Estimated cost of measuring arm D on the 12 evaluation tasks: about $1.5 to $2.5, plus about $0.5 to build the lessons from the
existing runs, inside the roughly $12.5 left of the allowance.

What would count as a result: a higher solve rate or a lower cost per verified fix than arm C, reported with the same caveat of one run per
task. If D does not beat B or C, that is reported too.
